# Saros 分阶段实施路线（ROADMAP）

| 版本 | 日期 | 说明 |
|---|---|---|
| v0.1 | 2026-08-14 | 初稿：三阶段演进路线（低代码验证 → Python 原型 → Java 生产化），结合 REQUIREMENTS.md / PLAN.md 细化 |
| v0.2 | 2026-08-14 | 用户确认决议：自研链路、二/三阶段共用 PG、G2 触发条件、阶段一采用 Coze、温柔陪伴语气验证项 |

## 1. 定位与文档关系

本文档定义 Saros 的**三阶段演进路线**：先做什么、每个阶段验证什么、什么条件下进入下一阶段。它不替代现有文档，分工如下：

```
REQUIREMENTS.md   需求：做什么、验收标准（v0.3，已含全部决议）
PLAN.md           阶段二的详细技术计划：架构/选型/里程碑 M0-M5/API/验证方案
ROADMAP.md（本文）演进路线：三阶段顺序、每阶段目标与交付物、决策门（Go/No-Go）
```

**演进逻辑**：每个阶段只投入「验证下一阶段决策」所需的最小成本 ——

- **阶段一（低代码）**验证**业务**：联网查询→总结→保存→复用 的闭环是否成立，AI 语气是否符合「温柔陪伴」；
- **阶段二（Python）**验证**技术架构**：数据本地可控、真长期记忆（pgvector）、RAG 检索质量；
- **阶段三（Java）**验证**规模化**：对外服务所需的高可用与工程化能力（条件性阶段，见 §5）。

## 2. 总体原则

1. **每阶段有明确决策门**：验收不通过不进入下一阶段；验收通过且下一阶段触发条件不成立，则停留本阶段（如阶段二后不必然进入阶段三）。
2. **资产可迁移**：每阶段的产出物必须是「下一阶段可直接复用」的资产（Prompt、字段设计、标签体系、API 契约、数据），不依赖平台/框架的私有功能。
3. **以本地 PG 为唯一真相源**：阶段一在云平台产生的数据仅用于验证，最终沉淀数据以阶段二起本地 PostgreSQL 为准。

## 3. 阶段一：低代码/无代码验证（预计 1-3 天）

### 3.1 目标：回答四个问题

| 编号 | 验证问题 | 对应后续决策 |
|---|---|---|
| Q1 | 「联网查询 → 结构化总结 → 保存 → 日后提问复用」闭环是否有真实价值、流程是否顺畅 | 决定整体方向是否值得自建 |
| Q2 | AI 总结/回答的语气是否符合**「温柔陪伴」**（不说教、不冷冰冰、像陪读伙伴） | 产出《语气与 Prompt 规范》，回写需求文档 |
| Q3 | 平台自带知识库检索（关键词/语义）质量是否够用 | 决定阶段二混合检索的投入重点 |
| Q4 | 导入历史文章/笔记后，AI 总结的准确度与可复用性 | 验证「知识库冷启动」方案 |

> 注：「温柔陪伴」语气为本次新增验证目标（REQUIREMENTS.md 未显式收录），✅ 已确认在阶段一验证（2026-08-14），验证通过后回写需求文档 §2，并作为 Prompt 规范附录。

### 3.2 工具选型

| 方案 | 优点 | 缺点 | 定位 |
|---|---|---|---|
| **Coze（扣子）** + 飞书多维表格 | 微信/飞书一键发布，最快拿到「可直接对话的雏形」；知识库可直接挂载飞书多维表格 | 数据在云平台；工作流定制受限 | **✅ 已确认（2026-08-14）**：交付物就是「飞书或微信里对话的 Saros 雏形」 |
| Dify（自托管） | 开源、数据本地，最贴近阶段二自研架构，RAG 引擎可控 | 微信/飞书接入需自行处理；上手稍慢 | 备选（暂不采用），仅作记录 |
| 纯飞书多维表格自动化 | 零学习成本 | 无对话入口，无检索能力 | 仅作存储层，不单独成方案 |

✅ 已确认方案：**Coze（扣子）+ 飞书多维表格**（用户确认，2026-08-14）。Dify 暂不采用，仅作备选记录。

### 3.3 工作流设计（Coze 为例）

```
用户提问（飞书/微信 Bot）
  → 节点A 联网搜索（必应搜索/头条搜索插件，取 top 8）
  → 节点B 知识库检索（挂载飞书多维表格为知识库，召回历史总结 top 5）
  → 节点C LLM 合成回答（Prompt 要点：引用来源标注；沉淀知识与搜索结果
        冲突时以沉淀为准并说明；资料不足明说；温柔陪伴语气）
  → 节点D 结构化输出（JSON：回答 / 一句话总结 / 3-5 个中文标签）
  → 节点E 落库：总结+标签写入飞书多维表格（沉淀），回答返回用户
```

飞书多维表格字段建议（直接对应阶段二数据模型）：

| 字段 | 类型 | 说明 |
|---|---|---|
| 记录ID | 自动编号 | 与阶段二 knowledge_points 对应 |
| 类型 | 单选 | 问答沉淀 / 文章笔记 / 视频笔记 |
| 内容 | 多行文本 | 原始内容或提问 |
| AI 总结 | 多行文本 | 节点D 输出的结构化总结 |
| 标签 | 多选 | 与阶段二共用标签空间同构 |
| 来源链接 | 文本 | 搜索来源或原文 URL |
| 创建时间 | 日期 | — |

### 3.4 知识库冷启动

- 导入 **20-50 篇**已积累的文章/笔记（低敏内容优先）到飞书多维表格并挂为知识库；
- 抽查 AI 总结：准确度（有无幻觉捏造）、语气（温柔陪伴）、总结粒度（一句话 vs 一段话）；
- 根据抽查结果迭代 Prompt（温度、人称、总结长度），**每次修订记录变更**。

### 3.5 阶段交付物与验收标准

交付物：① 可在飞书/微信直接对话的 Saros 雏形；②《Saros 语气与 Prompt 规范》v1；③ 飞书表格字段设计与首批沉淀语料。

| 编号 | 验收项 |
|---|---|
| A1 | 完成 ≥10 次真实问答，抽样人工核对来源引用正确率 ≥ 80% |
| A2 | ≥5 条总结沉淀入库，之后的新提问能自动关联引用旧总结（复用闭环成立） |
| A3 | 语气自评符合「温柔陪伴」预期，或已找到稳定的 Prompt 配方 |
| A4 | 冷启动导入 ≥20 篇，总结抽样可读、无编造 |

### 3.6 风险与注意

- ⚠️ 云平台与 NFR-1「数据不出本机」冲突：本阶段**仅导入公开/低敏内容**，敏感私人笔记留到阶段二直接进本地库；验证期数据可随时丢弃。
- 平台功能/价格可能变化：Prompt、字段设计等关键资产随时导出保存到本仓库 `docs/`。
- 不要把平台私有功能做成永久依赖：一切产出以「可迁移资产」形式沉淀。

## 4. 阶段二：Python 原型（预计 2-4 周）

### 4.1 目标与文档关系

摆脱平台限制，实现数据本地、代码全控、真长期记忆（pgvector）的 AI 后端原型。**本阶段的详细技术计划即 PLAN.md（M0-M5）**，本节只记录与三阶段路线相关的决策调整。

### 4.2 对原设想的调整（2026-08-14 全部确认）

| 原设想 | 调整 | 依据 |
|---|---|---|
| 引入 LangChain/LlamaIndex 框架 | **✅ 走自研轻量链路**（openai SDK + 手写混合检索），不引入框架；仅在日后需要 rerank / 复杂 Agent 编排时再评估 LlamaIndex 单点引入 | 用户确认（2026-08-14）：依赖少、调试透明、国产模型兼容好；混合打分 0.6/0.3/0.15 加权是框架默认行为给不了的 |
| Docker 部署 PostgreSQL + pgvector | **✅ 阶段二与阶段三共用同一个本地部署的 PG**（pgvector 已启用、512 维），不用 Docker 部署；Docker Compose 仅作换机/协作时的可移植性备选 | 用户确认（2026-08-14）；REQUIREMENTS §9.2 决议：PG 已在本地 Linux 搭建，连接走 .env |
| FastAPI 或 Flask | **FastAPI** | ✅ PLAN.md 已定（SSE 流式支持好） |

### 4.3 行动计划（对应原设想四步，映射到里程碑）

| 原设想步骤 | 落地内容 | 里程碑 |
|---|---|---|
| 环境准备 | 确认 PG 网络可达 + `.env` 配置（PG_*、LLM_*、AUDIO_LLM_*）；嵌入模型下载（国内设 HF 镜像）；前后端脚手架 | M0 |
| ETL 流程（分块→向量化→写 pgvector） | 模块四：schema 脚本建表（不用 alembic）→ BGE 嵌入 → pgvector 写入；**追加**：阶段一飞书表格导出 CSV → 批量入库脚本，使阶段一沉淀语料落地本地 | M1 |
| RAG 链路打通 | 混合检索：`0.6*cosine + 0.3*lex_overlap + 0.15*tag_hit`，阈值 0.35 取 top 5；冲突以沉淀为准；SSE 流式输出；自动标签 | M2 |
| API 暴露 | FastAPI 封装 RESTful + SSE（API 契约见 PLAN.md「API 概要」，即阶段三的对齐基准） | M2-M4 |
| —（原设想之外） | 模块二网页出题（M3）、模块三 B站视频（M4）、打磨（M5） | M3-M5 |

### 4.4 阶段交付物与验收标准

交付物：本地 Web 应用（数据不出本机），具备混合检索的真长期记忆后端。

验收标准：**REQUIREMENTS §10 四条核心闭环**（手录禁粘贴→提问带引用→网页出题→B站归档可跳转）+ M5 日常可用（设置页、README、测试）。

### 4.5 决策门 G1 回顾与 G2 预告

- 若阶段一验证发现平台限制（数据量、定制、成本）已成为主要矛盾 → 可**加速**进入阶段二（M0 与阶段一并行）。
- 阶段二完成后**不必然**进入阶段三，触发条件见 §5.1。

## 5. 阶段三：Java (Spring Boot) 生产化（条件性阶段，预计 2-4 周）

### 5.1 触发条件（决策门 G2，✅ 用户确认 2026-08-14）

阶段二搭建完成后**不必然**进入阶段三——**仅当出现工程化能力需求时才启动**。典型触发信号：

1. 对外提供服务（多用户/团队协作等）；
2. 需要生产级工程能力：安全鉴权、监控体系、缓存等；
3. 遇到真实性能/维护瓶颈（非猜测性焦虑）。

⚠️ 当前需求非目标仍是「多用户与账号体系、云端部署」（REQUIREMENTS §2），无上述信号则**停留阶段二**——对单用户本地工具而言，Python 方案已是最优投入产出比。

### 5.2 技术选型与架构决策

| 事项 | 决策 | 说明 |
|---|---|---|
| 框架 | **Spring AI 起步**，JBoltAI 按需引入 | Spring AI 与现有 openai 兼容接口同源（DeepSeek/Qwen 直接配）；JBoltAI 模型编排更强但生态绑定深，仅当编排需求确实复杂再引入 |
| 架构形态 | **单体优先**，按领域分包（saros-qa / saros-knowledge / saros-webpages / saros-videos） | 原设想提及微服务：当前规模单体足够，保留清晰模块边界以预留拆分空间 |
| 向量集成 | PostgreSQL JDBC + `com.pgvector:pgvector` + MyBatis VectorTypeHandler | **PG 表结构不变、数据零迁移**——阶段二积累的沉淀与问答历史直接可用 |
| 多模型协同 | 自实现 ModelRouter：主模型 + 备用模型，超时/限流/5xx 自动切换回退 | PLAN 中「LLM 可配 + 容错重试」的升级版；主备均走 OpenAI 兼容协议 |
| 安全 | Spring Security **仅当多用户时引入** | 当前单用户本地（NFR-6 无需登录），提前引入徒增复杂度 |
| 缓存 | Redis 高频问答缓存**可选** | 单机场景收益有限，先不做，出现瓶颈再上 |
| 监控 | Prometheus + Grafana **按需**；起步用 Spring Boot Actuator | 本地单机先用 Actuator 观察即可 |
| 前端 | **Vue 3 前端不动**，反向代理 `/api` 指向 Java 服务 | 以阶段二 API 契约为准，Java 侧写契约测试对齐 |

### 5.3 迁移策略：绞杀者模式（Strangler）

```
阶段三启动
  → J0 骨架：Spring Boot + 配置 + health + 契约测试（对齐阶段二 OpenAPI）
  → J1 迁移 knowledge/tags（读多写少，先易后难）
  → J2 迁移 qa（SSE 流式对齐）
  → J3 迁移 webpages/videos（含异步任务队列，Spring @Async / 虚拟线程）
  → J4 多模型路由 + 监控
  → J5 全量切换：前端指向 Java 服务，Python 服务退役归档
```

原则：PG 数据全程共用、前端无感知、逐步接管 `api/*`，任一环节不达标可回退。

### 5.4 阶段交付物

- 可对外提供服务、具备（按需裁剪的）监控与安全机制的 Java 生产级后端；
- Python 原型退役归档（保留 `git tag` 与 README 说明）；
- 前后端分离部署文档（替代 dev.sh 的本地起法）。

## 9. 已确认决议（2026-08-14）

1. ✅ 阶段一平台：**Coze（扣子）+ 飞书多维表格**；Dify 暂不采用，仅作备选记录
